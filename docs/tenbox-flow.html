Tenbox Task Flow

What happens to one task, step by step: who acts, where it runs, what gets created, and what must be true before the next step. The example task is TEN-301 in the my-app project.

1Startdaemon 2Planmaster → you 3Buildworkers 4Checksdaemon 5Reviewreviewer 6TryQA + sandbox 7YouPR + links 8Closedaemon
needs your decision plain code, no LLM agents work A failure in steps 4 to 7 goes back to the master, who sends a fix to step 3. The stages are the master's recipe; the daemon only enforces the gates.

What exists at each step

Every resource is created as late as possible and removed as early as possible. Only rooms in step 6 and 7 run a full stack.

The steps

Step 1

Start

daemon
Trigger
You drag a Linear task into an empty room, or run tenbox start TEN-301.
Who
The daemon. No agent yet.
Creates
Task worktree and branch feat/TEN-301 from main. The .tenbox/ folder. One tmux session for the room. The master window.
Sandbox
None.
# what the daemon runs
git -C ~/wt/my-app/main worktree add \
  ../TEN-301 -b feat/TEN-301 main
mkdir ../TEN-301/.tenbox  # task.md from Linear
tmux new-session -d -s tenbox-TEN-301 \
  -n master -c ~/wt/my-app/TEN-301 \
  'claude --append-system-prompt "$(cat ~/tenbox/roles/master.md)"'
# Linear: TEN-301 → In Progress
Step 2

Plan

masteryour approval
Who
Master, window :master, in the task worktree.
Reads
task.md, decisions.md, the code, openapi.yaml, tenbox.yaml.
Writes
.tenbox/plan.md
Asks
Anything the task does not decide goes through ask. Product, contract and risk questions come to you.
  1. Steps and the files each one touches.
  2. Acceptance criteria, written so QA can test them from outside. Example: "Cancelling an already cancelled order returns 409."
  3. Proposed OpenAPI changes, as a diff. The spec is locked, so only you can approve them.
  4. Split: one worker, or several in parallel with separate files.
  5. Which sandbox profile step 6 needs.
GateYou approve the plan in the panel. If the plan changes the spec, you approve that too.
If notYour comment goes to the master. It revises plan.md and asks again.
Step 3

Build

workers
Who
Workers the master spawns with spawn_agent(worker, part). One tmux window each.
Where
One worker: works directly in the task worktree.
Several: each gets its own worktree and branch from the task branch, so no two agents write the same files at once.
Does
Writes code and unit tests. Commits on its own branch. Writes .tenbox/agents/w1/result.md: what changed, how it was tested.
Sandbox
None. If integration tests need a real database, the dev profile starts only the DB.
# parallel workers
git worktree add ../TEN-301--w1 -b feat/TEN-301--w1 feat/TEN-301
tmux new-window -t tenbox-TEN-301 -n w1 \
  -c ~/wt/my-app/TEN-301--w1 'claude ...worker.md'

# when a worker is done, the master merges
git -C ../TEN-301 merge --no-ff feat/TEN-301--w1
git worktree remove ../TEN-301--w1

Locked paths (openapi.yaml, e2e/) are blocked by a hook. A merge conflict the master cannot resolve becomes a question to you.

Done whenEvery worker branch is merged into feat/TEN-301 and the master moves on.
Step 4

Checks

daemon, no LLM
Who
The daemon runs the commands from tenbox.yaml on the task branch. An agent cannot fake the result.
Runs
Type check, lint, unit tests. wtbase compares with the main baseline, so only new failures count.
Writes
.tenbox/rounds/1/checks.json
Sandbox
None.
# tenbox.yaml
checks:
  types: pnpm tsc --noEmit
  lint:  pnpm lint
  unit:  pnpm test --run
GateNo new failures.
If notThe failures go to the master. It sends the fix to a worker: back to step 3, round 2.
Step 5

Review

reviewer
Who
A new reviewer session each round, window :reviewer. It cannot edit files. It never sees the workers' reasoning, only the result.
Reads
plan.md, the diff main...feat/TEN-301, checks.json, decisions.md.
Writes
.tenbox/rounds/1/review.json: score, must-fix list, nice-to-have list.
Also
The daemon pushes the branch and opens a draft PR. The PR body holds the plan, decisions and review.
{
  "score": 72,
  "verdict": "revise",
  "must_fix": [
    "POST /orders/{id}/cancel returns 200 for an already
     cancelled order; plan says 409"
  ],
  "nice_to_have": ["debounce value is hard-coded"]
}
GateScore at or above pass_score, no must-fix items, and the reviewer did not edit the code.
If notThe must-fix list goes to the master, then to a worker: step 3. After max_rounds the room asks you.
Step 6

Try

sandbox upQA
Sandbox
The daemon pins the current commit, for example a1b2c3d, and builds the sandbox from it. It does not mount the worktree, so the tested code is exactly the code that will merge.
Runs
The try profile: api, panel, db, fakes, on an internal network. Seed data and demo accounts. Each service gets a p<port> link.
Who
A new QA session, window :qa. A black-box tester: it cannot read the code. It sees the task, the acceptance criteria, the OpenAPI spec and the links.
Writes
.tenbox/rounds/1/qa/report.md and evidence: requests and responses, screenshots, log lines, DB rows.
  1. Calls the API for every acceptance criterion.
  2. Clicks through the UI with Playwright MCP if the frontend changed.
  3. Switches fake scenarios: card_declined, timeout_30s.
  4. Behaviour the spec does not define becomes a question to you.
  5. Writes a "how to try" note for you: links, demo accounts, scenario switches.
git archive a1b2c3d | docker build -t tenbox/TEN-301 -
docker compose -p tenbox-TEN-301 --profile try up -d
GateEvery acceptance criterion passes, with evidence for the tested commit.
If notThe report goes to the master, then to a worker: step 3. The next round builds a new sandbox from the new commit.
Step 7

You

your decision
Trigger
The room turns amber and you get a notification. The PR moves from draft to ready. Linear moves to In Review.
Code
Read the GitHub PR: diff, line comments, CI.
App
Open the sandbox links and try it yourself. Same commit QA tested.
History
The panel: who changed which file, decisions, review, QA evidence, every terminal.
Deep look
code --remote ssh-remote+devbox ~/wt/my-app/TEN-301
  1. Accept: approve the PR, or press Accept in the panel.
  2. Send back: "Request changes" or line comments on the PR, or a note in the panel. The master reads them and sends the fix to step 3.
  3. If you do not look for a while, the sandbox pauses to free CPU. Opening a link starts it again.
GateYour approval. Nothing merges without it.
Step 8

Close

daemon
Merges
Squash-merges the PR, updates ~/wt/my-app/main.
Removes
Sandbox and its volumes, the task worktree and branch, the tmux session.
Keeps
.tenbox/ and the agent logs go to ~/tenbox/archive/TEN-301/.
Linear
Done, with a work-log comment: rounds, scores, PR link.
gh pr merge feat/TEN-301 --squash --delete-branch
docker compose -p tenbox-TEN-301 down -v
git -C ~/wt/my-app/main worktree remove ../TEN-301
tmux kill-session -t tenbox-TEN-301

Decisions that apply to the whole project are proposed for the project CLAUDE.md. You approve them first.

The loop

Failures always return through the master. The master decides who fixes it. Only the failed stage and the ones after it run again.

flowchart LR
  S1[1 Start] --> S2[2 Plan] --> G1{you approve?}
  G1 -- no --> S2
  G1 -- yes --> S3[3 Build] --> S4[4 Checks] --> S5[5 Review] --> S6[6 Try] --> S7[7 You] --> S8[8 Close]
  S4 -- new failures --> M((master))
  S5 -- must-fix --> M
  S6 -- criteria fail --> M
  S7 -- request changes --> M
  M -- fix task --> S3
